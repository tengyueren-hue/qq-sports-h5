## 【一句话摘要】

为QQ运动用户提供每周运动总结，通过插件触达、首页轻量阅读和成绩卡分享，直观呈现一周的运动积累。

## 【需求背景】

QQ运动当前以每日步数、目标和排名为主，缺少对一周运动积累的统一回顾。穿戴设备用户还有活动、锻炼、站立及运动记录，尚未在周期报告内集中呈现。本期以周报连接数据总结、轻量阅读和社交分享。

## 【需求目标】

- 汇总周内每日步数、目标完成情况、好友对比和运动表现。
- 通过插件内容项和首页分时入口，让用户便捷发现周报。
- 通过同一份内容的底部弹窗与全屏阅读，降低进入成本。
- 根据实际数据展示运动类型、次数、时长及穿戴概览。
- 提供与周报一致的静态分享成绩卡及二维码回流。

## 【期望上线时间】

2026年10月，具体日期以项目排期为准。

### 2. 需求详细逻辑描述

#### 一、本期范围

1. 仅周报，不建设月报、月报发送、周/月切换、历史月份滑块及月度文案配置。
2. 基础页面复用模板包。新增插件内容项、周报、分享内容按本次Figma实现；首页入口及上滑交互沿用已确认规则。
3. 数据优先级为总结、分享、坚持激励。无AI生成文案、医疗判断、个性化运动处方。
4. 只使用每日步数，不使用每小时或每时段步数。
5. 实验覆盖用户均可获得周报；只区分“有任意有效数据”和“全部无数据”，不按步数高低、记录天数或达标天数设置文案分层。有效0值也属于有数据。
6. HTML是静态交互示例。图中数值用于视觉对照；线上必须统一计算，不将样例常量作为业务规则。

#### 二、生成、发送与周期

| 规则 | 说明 |
| --- | --- |
| 时区 | 北京时间（Asia/Shanghai） |
| 周期 | 上周一00:00（含）至本周一00:00（不含），即完整自然周 |
| 发送 | 每周一08:00，生成成功后发送一条周报插件消息 |
| 触达 | 插件消息/红点、QQ运动首页入口，不额外新增系统Push |
| 重试 | 生成失败不发送空卡；成功后补发。按用户+周起始日期去重，不重复发送 |
| 跨月跨年 | 仍按同一自然周统计，展示完整起止日期；跨年补全年份 |
| 首页入口 | 仅保留右上角“报告”，不展示首页顶部强入口 |

消息标题“上周运动周报”；周期“{开始月日}–{结束月日}”。重新打开/更新数据不重新发送。首页顶部入口及其24小时收缩规则已取消。

#### 三、打开时刷新数据

1. 每次打开周报均重新加载该周期最新源数据，包括延迟同步和补卡结果。刷新不改变统计周期。
2. 首次无缓存时展示加载态；有上次成功数据时先显示缓存，随后整体更新，避免各模块新旧版本混用。
3. 数据更新成功后显示更新时间。失败保留旧数据并提供重试；首次加载失败展示失败页。
4. 展开至全屏、收起、打开/关闭分享面板不视为重新打开报告，不重复刷新或跳到顶部。
5. 分享图片使用生成时的一致数据快照；已发送图片不变。扫码在线报告打开时重新加载其对应周的数据。
6. 部分穿戴数据延迟，展示现有有效数据并提示；缺失不当成0。

#### 四、插件页入口

1. 增加独立周报消息内容项：报告图标、“上周运动周报”、统计日期、“查看周报”及箭头；发送时间复用消息时间展示。
2. 按设计在现有内容卡提示区域增加“上周运动周报 / 去查看”一行，与独立消息指向同一期报告。
3. 不在入口额外叠加复杂统计、长说明或宣传文案。原有运动内容由现有能力提供，本需求不新增AI分析生成能力。
4. 任一周报入口点击后进入运动首页，首页就绪即自动弹出对应周报。不得进入另一份简版页面。
5. 首次成功呈现报告正文后标记该期已读，失败不清除未读；仅清除本需求对应未读，不影响插件其他消息红点。
6. 消息随现有插件消息机制保留；历史消息打开其原周报，不替换为最新一期。
7. 提示区仅保留周报、今日运动、捐步三项，不显示喝水提醒。消息卡随内容自适应高度；进入插件页定位最新消息，卡片与固定底栏间保留约12px间距，不保留删除内容后的空白。

#### 五、首页入口与时效

1. 不展示首页顶部周报入口，不再设置24小时强入口展示期。
2. 保留首页右上角“报告”文字入口，点击打开最新可用周报；原有个人主页入口保持可用。
3. 从插件点击周报进入首页后仍自动打开对应报告弹窗，普通进入首页不主动弹出。
4. 未读显示红点，已读不显示。无已生成周报时不显示空入口。
5. 已有历史插件消息仍能定位原报告。此前提出的历史列表需改为周维度，本次Figma未提供相应布局，入口与本期范围待产品确认。报告存储与消息保留周期沿用现有平台能力，具体期限待接口确认。

#### 六、弹窗与全屏交互

1. 初始以约74%可视高度底部弹窗展示完整报告顶部，首页背景保留遮罩。
2. 上滑时容器跟随手指连续增高；达到展开阈值后吸附全屏。完全展开前优先扩展容器，展开后继续滚动正文。
3. 弹窗与全屏共用内容、数据和组件实例，不切页面，不重新加载，不丢失当前阅读位置。
4. 顶部拖拽区域支持下拉收起；正文非顶部时，下拉先滚动正文，避免误关闭。遮罩、关闭/返回按钮可关闭。
5. 从插件打开后关闭报告，留在运动首页；再次返回遵循原导航栈。分享关闭回到原阅读位置。
6. 支持系统返回和无障碍按钮操作。小屏保证底部按钮、分享渠道可访问，不发生横向裁切。

#### 七、报告结构与数据规则

| 模块 | Figma内容 | 业务口径 |
| --- | --- | --- |
| 封面 | 头像、日期、主题文案、昵称、总步数、较上周变化 | 总步数为周期内每日最终有效步数之和；主题为配置文案 |
| 01 每一步，都算数 | 日均步数、完成目标、最佳排名、好友对比、每日步数图、活力日、估算距离/圈数/消耗 | 只绘制周一至周日7个每日数据，不增加小时维度 |
| 02 坚持，正在发生 | 7日达标圆环、日期及步数、最长连续达标、达标/中断天数、充能补卡 | 使用对应日期的目标及已有达标/补卡结果 |
| 03 运动，不止一种方式 | 穿戴概览、运动总次数/时长/消耗、高光运动、本周运动日、运动类型明细 | 依数据存在情况展示，无法计算的字段不补造 |
| 收尾 | 下一段足迹，等你续写、鼓励文案、分享本周运动报告 | 分享入口置于最后一张卡片；保留顶部分享图标 |

**1. 步数与比较**

| 指标 | 口径及异常 |
| --- | --- |
| 有效步数日 | 数据源明确返回该日期有效记录；有效0步计入，未授权/未同步/无记录不计入 |
| 总步数 | 7天有效记录之和；缺失日期图表展示“暂无记录”，不以0柱混淆 |
| 日均步数 | 7天齐全时总步数÷7并四舍五入为整数；不完整时用有效记录天数作分母，标注“已记录{N}天日均” |
| 环比 | 两周记录均完整且上周总步数>0时展示百分比；为0、缺失或不可比则隐藏；相等使用“与上周持平” |
| 完成目标 | 周内按当日目标判定的达标天数，与坚持模块一致；事后改目标不追溯改写旧日目标 |
| 最佳排名 | 周内有效每日好友排名的最优名次；不是周累计排名 |
| 周好友对比 | 需好友同周期累计步数比较能力。超过比例为严格低于本人累计步数的可比较好友数÷可比较好友数；不含自己，同分不计超过 |
| 排名文字 | “在{好友数}位好友里排名第{名次}”；需明确该数据是周累计排名；无该能力则隐藏好友对比卡，不由每日名次推算 |
| 活力日 | 有效每日步数最多的日期；并列取周内较早日。副文案可展示该日好友排名，与周排名区分 |
| 估算卡 | 仅复用已有可用距离/能量估算能力；无已确认口径时隐藏该字段或整卡。距离、跑道圈数、消耗均明确“估算”，不得写死换算系数 |

**2. 坚持与补卡**

1. 圆环按周一至周日排列，与真实日期、每日步数、当日目标对应；正常达标、未达标、已补卡、无记录清晰区分。
2. 达标天数、中断天数和最长连续达标均复用现有业务口径，补卡是否计入达标/连续以现有能力返回为准；步数不因补卡被改大。
3. 无记录日不直接断言未运动，不混入“中断天数”；展示“{N}天暂无记录”。目标缺失时隐藏目标判断。
4. “充能补卡”仅在存在可补日期时可点击，进入已有补卡流程；消耗、权限、期限、失败提示全部复用现有能力。
5. 从补卡流程返回后刷新该期，更新日历、天数及新生成的分享卡；失败/取消不改数据。

**3. 运动与穿戴**

1. 运动记录按开始时间所属日期归入周；跨午夜记录只归属一次。多来源重复记录沿用现有聚合去重能力。
2. 总次数为有效记录数，总时长为去重记录有效时长之和；缺少时长不计为0，标注“已记录时长”。消耗仅汇总有有效值的记录，缺失则注明范围或隐藏。
3. 运动类型按规范类型去重；每种展示图标、名称、次数、总时长。次数总和须与总次数一致，类型数须与实际明细一致。
4. “本周运动日”按周一至周日展示，运动日指至少一条有效运动记录的日期。同日多条只计1天；本设计用圆点标记有运动，运动图标集中用于类型明细。
5. 高光优先展示有可靠个人最佳标记的跑步记录；无个人最佳证据时不显示“个人最佳”。无跑步时可展示时长最长的一条有效运动；仅展示该类型真实提供的字段。
6. 跑步可展示距离、平均配速、时长及消耗；乒乓球、羽毛球等只有时间和时长时，展示实际可用信息，不生成击球数、配速等缺失字段。
7. 设备概览显示设备名、活动、锻炼、站立；这些是设备周概览，不与运动记录消耗相加。单位沿数据源，小时/分钟转换保持一致。
8. 本次Figma设备区域为概览与三环图标，原型先按提供的设计还原。此前确认的穿戴闭环日历并未取消，但本稿未提供对应布局，需产品与设计确认是否补入本期；不得据此默认为已取消。无设备数据隐藏概览，不要求用户绑定后才能看基础报告。
9. 设计“超过88%好友”的运动类型比较仅在具备可比较好友类型数据时展示，缺失即隐藏，禁止根据本人类型数推断。

#### 八、分享内容与回流

1. 点击顶部分享或收尾按钮，展示Figma指定的静态成绩卡预览与QQ原生分享面板；报告阅读位置保留。
2. 卡片包含头像、昵称、“运动数据简报”、总步数、日期、日均步数、完成目标天数、最佳排名、可用的周环比和最长连续达标、QQ运动标识及二维码。
3. 保留此前确认的用户主动切换分享模板需求。本次设计只提供“运动数据简报”一种模板，原型先实现该默认样式；其他模板及切换控件需补充设计后实现，是否在本期交付待产品确认，不默认为已取消。
4. 分享渠道、收藏、复制链接、二维码等功能复用QQ现有分享面板及可用能力，不由H5声称已发送；取消和失败分别反馈，成功以平台回调为准。
5. 分享图片保存生成时快照。二维码对应当前分享者、统计周及分享标识；线上内容可更新，但不得跳到分享者另一周。
6. 接收者可查看分享者该期报告内统计数据；“查看我的周报”需要登录QQ，并切换至接收者本人数据。接收者不显示分享者补卡等修改入口。
7. 分享范围是报告中展示的统计信息，不是运动原始数据接口；不包含精确路线、位置、设备标识。分享预览能让用户看到即将对外发送的内容。
8. 加载失败、分享图生成失败、无权限/链接不可用均显示可理解提示；不得将第三方失败当成功。原型二维码为设计素材，联调时必须替换为真实业务链接。

#### 九、统一无数据兜底与异常

| 场景 | 展示和处理 |
| --- | --- |
| 存在任意有效数据 | 统一使用当周配置文案，展示已有数据；不按步数高低、记录多少分层，不另加低数据提示。有效0值正常展示，不等同无数据 |
| 所有模块均无有效数据 | 使用唯一空态：标题“这一周，暂未收到运动记录”，说明“有记录后，再来看看你的运动周报吧。”；保留关闭/返回，不展示空成绩卡或分享按钮 |
| 无穿戴/无运动 | 隐藏对应空卡；保留步数与坚持，其他有数据模块继续展示 |
| 数据刷新中 | “正在更新本期数据…” |
| 更新成功 | “数据更新于{月日 时分}” |
| 更新失败有缓存 | “更新失败，已为你保留上次数据。”及“重新加载” |
| 更新失败无缓存 | “周报暂时加载失败，请重试。”及“重新加载” |
| 设备同步延迟 | “部分设备数据仍在同步，稍后打开可查看完整结果。” |
| 分享生成失败 | “分享图片生成失败，请重试。”及“重试” |

主题文案支持按统计周配置，不新增AI生成，不按步数高低、记录天数、连续达标天数选择文案。所有有数据用户使用同一套；未配置使用默认套组：头图“这一周，脚步很有光”，坚持说明“目标不是束缚，是你为自己点亮的小小约定。”，收尾小标题“下一段足迹，等你续写”，收尾正文“带着这一周的光，继续走走吧。”。只有全部无数据时替换为第九节统一空态。

数据句式仍按实际值填入变量；缺失字段隐藏，不补造0值或比较结论。这是字段可用性规则，不增加文案人群分层。加载/网络失败仍按错误提示处理，不误显示为无数据。

“好友前列”标签需明确阈值后开启；当前建议超过80%可比较好友时显示，**待产品确认**。未确认前仅展示有数据支撑的数字结论。

#### 十一、配置与验收

| 配置 | 规则 |
| --- | --- |
| 周报功能开关 | 需要，支持停止新触达和入口曝光 |
| 实验 | 接入现有实验平台；比例、扩量节奏由实验配置，不写死比例 |
| 首页入口 | 仅右上角报告入口，不设置顶部强入口时长 |
| 无数据判定 | 所有模块均无有效数据；有效0值不算无数据 |
| 主题文案 | 固定默认句，可按统计周配置 |
| 原生分享能力 | 依宿主版本支持的真实渠道呈现 |

验收重点：周一08:00及跨年周边界；补发去重；首页无顶部强入口；两个插件入口跳转；弹窗连续展开且内容一致；首次/再次刷新与失败缓存；只有每日步数；步数/日均/天数/分类汇总一致；有数据统一文案与全部无数据兜底；补卡返回刷新；分享取消/失败/成功及扫码归属；登录后本人数据隔离；小屏、黑夜模式和返回操作。

### 3. 是否有外部依赖

依赖每日步数、历史日目标及补卡结果、好友排名/可比较好友周期统计、穿戴数据聚合、运动记录去重、QQ插件消息与红点、现有分享及二维码、登录和实验平台。好友周比较、运动类型好友比较、估算公式是否已有服务支持需接口确认；未具备则按字段隐藏，不阻断基础周报。

### 4. 特性是否分期分迭代实现

本期完成周报触达、首页入口、弹窗/全屏、报告模块、指定分享卡及回流。不包含月报和AI能力。此前确认的历史访问、穿戴闭环日历和多分享模板在本次Figma中未提供完整设计，其周报形态与本期交付范围待产品确认；原型不擅自增加与本稿不同的视觉布局。

### 5. 是否涉及单独的 AMS 测试验收

待产品与配置平台负责人确认；当前尚无独立AMS页面或新增配置后台的明确需求。
